# KG 抽取经验库

这个文件由 Hermes 在每日审计后维护，内容会被自动注入 `kg-extract.md` 的「已积累的抽取经验」小节。
它是知识图谱质量的长期记忆：昨天被扣分的地方，今天变成硬规则。

维护规则：

- 每条经验写成**可执行的指令**，不要写感想。能写进审计器的规则就去改 `scripts/kg_audit.py`，写不进的才放这里。
- 条目格式：`- [YYYY-MM-DD] 指令。（触发原因：某次审计的具体扣分项）`
- 上限 25 条。超出时合并同类项、删掉已经连续 5 天不再复现的条目，保持 prompt 精简。
- 高频实体、易错命名、反复出现的主体写进「实体规范名对照」小节，这是跨文章连通的关键。

## 通用经验

- [2026-10-22] 公司内部的 AI 分部（如"某公司的 AI 部门"）应标注为分部/子组织类型，不要一律标成 company。
- [2026-10-22] 收购完成后的"能力并入某产品"事件不要用 partnership 类型，应归为 acquisition 或 integration。
- [2026-10-22] compared_with 只用于有性能/指标对比的证据；"两家做法或策略不同"不是性能比较，不应建 compared_with 边。
- [2026-10-23] 融资新闻要把原文具名的所有参与方（含博裕资本、IDG 资本等财务机构）都抽成实体并建立 invests_in 关系，不能只抽产业方或明星方；具名即主体。
- [2026-10-23] 子公司/分部实体不要用母公司全名做别名（如阿里云不要写 Alibaba/阿里巴巴），并与全局规范名注册表保持区分，避免母子公司被错误合并。
- [2026-10-24] 单方向开源社区/第三方提供资源接入（硬件访问、早期 API、数据或算力赠予）是单方生态扶持，不要用 partners_with；对等合作才用 partners_with，单方供给可用 supplies（供应商→客户）或仅以事件表达，避免把"提供了接入"读成"建立了合作"。
- [2026-10-24] 事件 participants 只能收事件内真实执行或被动执行/被作用的具名主体；报道媒体、旁观点评方、告诫劝勉方（如银行提醒客户勿交凭据）不得入列，role 取值（subject/object/partner）必须与原文立场一致。
- [2026-10-24] 盘点/列表类新闻中，正文逐一具名介绍的产品（包括列举句里出现的每一个名字）都应成组抽成实体，与已抽的同类产品保持对称；只抽有关系的明星项会在图谱里漏掉同样具名的次要主体。
- [2026-10-25] 墓园/失败清单类新闻里，多个主体被并列罗列不构成它们彼此竞争的证据，competes_with 只在原文明确描述竞争关系时使用。
- [2026-10-25] "与某产品一脉相承/同一战略主线"等描述产品延续性的措辞不等于归属关系（developed_by），归属必须由原文直接点明开发者。
- [2026-10-25] 同一家公司在同一天披露的两个独立动作（公开漏洞、通知受影响方）应拆成独立事件，不要压成一个。
- [2026-10-26] 由机构（AISI、ARC Prize 等）执行评测/审计的事实，机构与被评对象之间不要建任何动作型边——evaluated_on、supplies、targets 都不行；评测事实只放进 security/benchmark 事件、evidence 与 metrics。
- [2026-10-26] 模型发布新闻中「在某产品/工具里可用」的部署句（如「在 ChatGPT Work 与 Codex 里，同样的用量额度……干更多活」）只支撑产品集成关系（integrates：产品→模型），不能支撑「产品 --developed_by--> 公司」归属边；归属必须由原文直接点明开发者。
- [2026-10-27] 修正事件语义时label与type必须同步修改——事件名改成"同台演讲"而type仍留partnership等于没改; 合作类事件类型只能用于原文宣布的具体合作内容(产品、算力、投资、协议), 亮相类事实只进summary/evidence。
- [2026-10-27] 评测/测评类新闻必须为评测机构与被评对象连一条评测关系边(evaluates/evaluated_by), 评测机构不能只出现在实体表和事件participants里却零关系。
- [2026-10-27] 同一指标在原文不同位置数字矛盾(如summary与detail人数不同)时, 按各自口径分条记录并在value中注明来源不一致, 禁止合并成一个数或臆造"N中有M个"的子集关系。
- [2026-10-28] 资本开支/基建投入不要用 invests_in：invests_in 只用于外部投资方→被投方，集团对自家部门或产品线的资金投入应删除或用内部投入语义，且 evidence 必须明确指向被投对象而非全公司数字。
- [2026-10-28] 产品型实体（浏览器、硬件、框架等）不能作为观察、断言、表态的主体：发言主体必须是组织/团队/个人实体，且同一事实在事件和关系中的 source 必须一致，不能一个用产品一个用公司。
- [2026-10-28] 跨文章复用同一实体时，其属性关系（如 subsidiary_of 的父级）必须全局一致：成稿前检查同一对实体在不同文章里的关系 target 是否相同，公司层级关系统一指向最上层母公司。
- [2026-10-29] 原文未标明某开放协议/标准/工具的开发者时, 不要建 developed_by 关系, 接入关系用 integrates/uses 表达。
- [2026-10-29] 同一新闻事实在多篇文章出现时, 只在其为主报道的文章中建立事件, 其他文章中的背景提及不要重复建事件。
- [2026-10-29] 新闻的核心主体(新定价路径、新档位、新组织等)必须进入实体层并尽量有边, 不能只在 metrics 或事件摘要里出现。
- [2026-10-30] 平台类产品(Facebook/Instagram/WhatsApp 等)与母公司的关系不要用 released_by，除非原文明确报道母公司当日发布了该产品；无签约式仅表达归属的新闻关系应省略或改用拥有类类型。
- [2026-10-30] 综合/观察类文章的核心论点若同时点名了几组主体（如能力侧与资金侧对照），每一侧明确点名的关键主体都要进 entities/events，不能只抽标题首发侧，否则丢失跨篇连通与论点完整性。
- [2026-10-30] 对"承诺未来发布但尚未存在"的产物（报告、标准、阶段性承诺）不要标成 developed_by 之类的完成态关系，改用计划/承诺类表述或直接省略。
