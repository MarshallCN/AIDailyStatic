# KG 抽取经验库

这个文件由 Hermes 在每日审计后维护，内容会被自动注入 `kg-extract.md` 的「已积累的抽取经验」小节。
它是知识图谱质量的长期记忆：昨天被扣分的地方，今天变成硬规则。

维护规则：

- 每条经验写成**可执行的指令**，不要写感想。能写进审计器的规则就去改 `scripts/kg_audit.py`，写不进的才放这里。
- 条目格式：`- [YYYY-MM-DD] 指令。（触发原因：某次审计的具体扣分项）`
- 上限 25 条。超出时合并同类项、删掉已经连续 5 天不再复现的条目，保持 prompt 精简。
- 高频实体、易错命名、反复出现的主体写进「实体规范名对照」小节，这是跨文章连通的关键。

## 通用经验

- [2026-11-05] 当新闻仅表述主体'寻求/谈判/考虑/有意'做某事而未被证实发生时，不要输出已成事实的关系（uses/acquires 等），只保留事件或用表达意图的关系（seeks_to_use/negotiating_for），更不放高权重。
- [2026-11-05] '通过某产品/API 开放、上架、分发'是渠道而非集成事实，不要据此输出 A --integrates--> B 的集成关系；确需表达时用提供访问/分发的渠道类关系，或只在事件 summary 里说明。
- [2026-11-05] why_it_matters 中的数字必须与本文关键指标（metrics/正文）口径一致，避免同一篇内出现互相矛盾的表述。
- [2026-11-06] 信用背书/担保类新闻：背书方与被担保方之间要建直接关系边（如 backs），不要把 credit support 抽成 partners_with 这类对等兜底类型。
- [2026-11-06] 标准/草案类新闻：实体名用标准本身的标识（如 __usage_ai-training），不要把承载它的工作组名（如 AI Preferences）当作标准实体，工作组与标准是两类不同实体。
- [2026-11-07] 合并/SPAC/收购类新闻，参与合并或交易的双方主体都必须建 relation（如 merges_with、acquires），不能只把其中一方放进 event participants 而漏掉连线。
- [2026-11-07] 把机构研报里的'警告/评论'抽象成关系时不要用 targets（针对）这类对抗性类型，仅在确有指向性对抗对象时使用；泛泛评论应删除该边或降级为事件论述。
- [2026-11-07] 同一篇论文/同一研究的多个发现不要各拆成一个 research 事件，应合并为一个事件概括核心主张，避免互相重复。
- [2026-11-08] 实地探访/到访/现场考察类报道（如团队去园区参观）不要构造成 reviews 关系；只有原文含评价、评测或打分内容才用 reviews，否则删边或用 visits/考察类语义。
- [2026-11-08] 把"分析师认为/据称/疑似是某方关联方"的未证实指控，不要在关系层断言为既定的 affiliated_with/partner；用疑似或 alleged 语义表达并保留"据称"字眼、降低权重。
- [2026-11-08] A 从 B 手中承接/接管 B 向 C 订购的订单时，实际供货方是 C，不要把被接管订单的 B 写成 A 的 supplier；供应链按真实交付方建模，订单转移用 acquisition/takeover 语义。
- [2026-11-09] 场所/设施类主体（DRAM 工厂、数据中心、测试产线等）应标为 organization 或 facility，不要标成 hardware/product。
- [2026-11-09] 丑闻/调查类新闻须抽取核心当事人为实体（含仅以背景身份提及但构成故事钩子的关键人物），不能只抽到与之相关的主流通用人物。
- [2026-11-09] 人物实体的 evidence 必须是描述该人物自身身份或行为的句子，不得引用描述其与他人关系或他人行为的句子。
- [2026-11-10] 若一篇新闻里后一个事件只是对前一个事件技术细节或内容的展开而非新的独立动作，应合并进同一事件，不要把同一动作拆成互相重复的多个事件。
- [2026-11-10] 事件 participants 的角色（如 regulator）必须与该事件的实际主体一致；不要因为整篇文章主题涉及某主体就把它与不相关的事件绑定。
- [2026-11-10] 关系类型的 evidence 必须直接支撑该关系语义；“延续某策略/定价续接”这类证据支撑定价参照而非模型能力对比，不要据此建立 compared_with 之类关系。
- [2026-11-11] 同一对主体之间的同一事实不要用一对方向相反的边重复表达（如 client 关系既写 supplies 又写 uses），只保留语义最具体的一条。
- [2026-11-11] 当某产品/模型/技能是作为 Skills 被托管进某个平台时，方向应写 产品 --integrates--> 平台，不要把承载平台写成集成方。
- [2026-11-12] 阻止/限制类新闻只保留平台方指向 agent 的一条关系边（如 restricts）；agent 使用的是平台或服务而非公司组织本身，不要反向补 agent --uses--> 公司实体 的边。
- [2026-11-12] 一个事件只承载自己的动作与后果，不要在本事件 summary 里写入另一个事件的结论（如把股价市场反应写进董事会事件），同一篇新闻的事件之间内容要互斥。
- [2026-11-12] 新闻中作为对比基线出现的前代或同类模型，要在 relations 里建 compared_with 边把对比关系固化进图（如 GPT-6 Cyber --compared_with--> GPT-5.6 Cyber），不要只把对比数字留在 metrics 里。
- [2026-11-13] 把机构预测、分析师判断、项目展望这类前瞻性论断抽成事件时，type 不要用 policy/launch 等表示已发生动作的类型，用 research/analysis 并在 label 中保留『预计/可能/将』措辞，metrics 的 value 也要保留不确定性。
- [2026-11-13] 同一篇里并列的独立事实（如订单延期与股价下跌）要拆成不同事件，只有原文明确建立因果时才能在 label 里用『致』，否则只作并列陈述。
- [2026-11-13] 事件 participants 中出现的每个实体必须同时出现在该篇 entities 列表里，不得跨文章悬空引用；跨文章复用的主体要在每一篇内都单独抽出来。
