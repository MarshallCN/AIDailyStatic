# KG 抽取经验库

这个文件由 Hermes 在每日审计后维护，内容会被自动注入 `kg-extract.md` 的「已积累的抽取经验」小节。
它是知识图谱质量的长期记忆：昨天被扣分的地方，今天变成硬规则。

维护规则：

- 每条经验写成**可执行的指令**，不要写感想。能写进审计器的规则就去改 `scripts/kg_audit.py`，写不进的才放这里。
- 条目格式：`- [YYYY-MM-DD] 指令。（触发原因：某次审计的具体扣分项）`
- 上限 25 条。超出时合并同类项、删掉已经连续 5 天不再复现的条目，保持 prompt 精简。
- 高频实体、易错命名、反复出现的主体写进「实体规范名对照」小节，这是跨文章连通的关键。

## 通用经验

- [2026-09-26] 关系类型要与语义精确匹配：为客户提供压力测试/评测是服务关系，不要复用 compute 供应（如 supplies）类关系；也不要让去指导自主研究的动作与分析师'使用'模型共用同一个 uses 边。
- [2026-09-27] 学术会议、竞赛等场合名（如 CICAI、NeurIPS）实体类型应标为 conference/event，不要标成 organization；「被会议接收」的语义用 accepted_at/featured_at，不要用 published_on 这类发布平台关系。
- [2026-09-27] 原文「与 X 一起指向同一判断」「结论一致」这类观点呼应，不等于两者被比较，禁用 compared_with 连接仅互相印证的实体；compared_with 只用于原文明确把双方放在一起做对比的场合。
- [2026-09-27] 事件标签描述的事实必须与其首要 evidence 指向同一件事：旧事件（如上周的漏洞演示）只作背景/metrics 归入说明，不要把它当成本周新事件的标签主体，避免旧背景与新事实揉成一条边界不清的事件。
- [2026-09-28] 背书/支持关系的主体是背书方：当原文是「A 公司支持使用该方案/获 A 背书」时，A 是 source、被背书的方案/组织是 target，写 company --supports--> platform 而非 platform --supports--> company，direction 必须与 evidence 的主动方一致。
- [2026-09-28] 「模型可在某硬件上运行」「某软件将运行在某硬件上」是可运行性描述，应建模为 runs_on（软件是 source、宿主硬件是 target），不要写成 uses；uses 只保留给原文构成真实技术依赖的情况。
- [2026-09-28] 许可证名（如某某 Community License）是授权条款而非其授权主体，不要作为公司/产品的 alias 合并；如需建模应抽为独立实体或仅在事件文本中说明。
- [2026-09-29] 同一天/同一公司同时被提及多个同基名的不同模型（如 GPT-6 Astra 与 GPT-6.1 Astra）时，模型别名必须彼此唯一、不得共用，否则跨文章实体合并会张冠李戴并讲出相反的故事。
- [2026-09-29] 报告/评测类原文里具体的数字指标（如 TPOT、吞吐提升）必须归因到原文明确写出的那个组件（引擎或芯片），不要把数字张冠李戴给邻近提到的其他组件；事实数字要与 metrics 一致。
- [2026-09-29] 当原文用「被怀疑」「尚未证明」「可能」等措辞表达推测而非事实时，不要把它固化为确定性的关系边，或必须显式标注为低置信推测。
- [2026-10-01] 把"受启发于"(inspired by)建模成关系时，应选用引用/借鉴类弱关系，不要用 built_on 这类暗示架构或运行时依赖的强关系，否则夸大主体间关系。
- [2026-10-01] 数据库、数据集、语料库等分析对象资源不该标成 product，应归为 dataset/database 类型，并保持与"被分析对象"的语义一致。
- [2026-10-01] 代理产品与其母体聊天模型是不同的实体：竞争、能力归属等关系必须挂在具体产品（如 Grok Bot）上，不要拿聊天模型（Grok）替身建模，避免同一竞争对被多篇用不一致主体重复建模。
- [2026-10-02] 安全与越权类新闻里，模型/代理越权访问受害方系统的，关系要用表示未授权访问或入侵的边（如 unauthorized_access / intruded_into），不要用 disclosed_vulnerability_in——披露行为人与入侵者往往不是同一方，读成"披露漏洞"会把故事讲反。
- [2026-10-02] 被一方聘为独立评估/审计机构的第三方，关系用 contracts_with 或 employs（或反向 evaluates），不要用语义空洞的 uses 兜底把雇佣评估关系吞掉。
- [2026-10-02] 仅凭两方"融资上市进程被对照"或"同日发布同类产品"就建 competes_with 是把共同出现/并列误当竞争——competes_with 需要原文有直接的竞争表述，否则删边或改用更弱的对照关系。
- [2026-10-03] 观察/汇总型新闻里，不要把同处一侧（同为本地模型、同为云巨头）的两个主体连成 compared_with；compared_with 只在原文对这两个具体主体作了直接对比时才用，阵营对立要表达为"本地 vs 云端"的整体 trend 而非 pairwise 比较边。
- [2026-10-03] 数据中心、园区、发电等基建项目实体应标为 project/infra 类类型，不要标成 product；product 只用于可售的软件或硬件商品。
- [2026-10-03] 不同 CVE 编号对应不同的独立漏洞，即使被同一攻击者链式利用，也不得合并为一个规范名；CVE 变体只能作为该 CVE 的 alias。
- [2026-10-04] 当某主体只在新闻中作为背景或相关事件被提及、而非本条的动作主体时，不要为它在本篇建立 developed_by 等实质关系，也不要把它所在段落的因果表述（如「该变化源于 X 引发的争议」）当作支持该关系的证据；关系证据必须读自本条原文能直接读出该断言的句子。
- [2026-10-04] 月度回顾/汇总类稿件除抽取领衔模型发布外，还应把文中非模型的标志性举措（如首个双盲评估试点、专项防御项目）独立成事件或补为主体，不能只聚焦模型而漏掉安全/评估侧信号。
- [2026-10-04] 为「某主体 A 由 B 开发/隶属 B」这类从属或开发关系提供证据时，该证据必须来自能直接读出开发或隶属语义的原文，活动性、归因性或因果性表述都不是有效证据。
- [2026-10-05] 同一产品发布的多个侧面（部署、配套设施、地点规划）应合并为一个事件，并把核心产品本身抽为实体；不要把单次发布拆成多个重复事件。
- [2026-10-05] 冷启动背景（上一周已签署的行政令、早前已发生的事件）不应列为当日事件，只在相关事件 summary 中作为语境提及。
- [2026-10-05] competes_with 等竞争关系需要原文存在直接对比竞争表述作为证据，不能用'对抗某国/某阵营'的叙事性概括兜底。
