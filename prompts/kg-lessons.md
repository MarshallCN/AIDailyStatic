# KG 抽取经验库

这个文件由 Hermes 在每日审计后维护，内容会被自动注入 `kg-extract.md` 的「已积累的抽取经验」小节。
它是知识图谱质量的长期记忆：昨天被扣分的地方，今天变成硬规则。

维护规则：

- 每条经验写成**可执行的指令**，不要写感想。能写进审计器的规则就去改 `scripts/kg_audit.py`，写不进的才放这里。
- 条目格式：`- [YYYY-MM-DD] 指令。（触发原因：某次审计的具体扣分项）`
- 上限 25 条。超出时合并同类项、删掉已经连续 5 天不再复现的条目，保持 prompt 精简。
- 高频实体、易错命名、反复出现的主体写进「实体规范名对照」小节，这是跨文章连通的关键。

## 通用经验

- [2026-09-16] 成立联盟、机构、学院的新闻中，机构作为 target 使用 founded_by（谁创立了它），不要用 developed_by 兜底。
- [2026-09-16] 数据中心、工厂等设施主体不要标注为 product；认证标准、测试框架不要标注为 policy，先核对主体真实类别再定 type。
- [2026-09-16] 不要把同一主体在同一新闻中的同类观点拆成多个重复事件；主题一致的 trend 事件应合并。
- [2026-09-17] 括号里仅作为并列举例出现的协议名（如"（如 MCP/A2A）"）不构成关系依据，同一句话共同出现不等于有关系；没有实质交互行为支撑就不要为其建立 compared_with / uses 等边。
- [2026-09-17] 硬件/基础设施新闻中，每个被赋予独立型号与具体数量的配置组件（如 Rubin GPU 与 Vera CPU、Blackwell Ultra 与 Rubin 分列）都要分别抽成独立实体并各自建 developed_by 边，不能只抽其一。
- [2026-09-17] 事件参与者的角色标签 partner 只能用于原文明确建立的合作关系，competitor 只能用于明确的对立关系；仅被提及的环境主体、对比参照对象应标为 context 或 object，勿用 partner/competitor 臆造合作或对立。
- [2026-09-18] '区别于/作为另一条路线/替代选择'这类定位性表述不能外推为 competes_with，只有原文明确陈述竞争或对抗时才建立竞争类关系，否则删除或使用更松的关系。
- [2026-09-18] 论文类文章中仅作背景语境顺带提及的产品与公司（如论述动机时提到的其他产品）与论文主体没有实质关系，不应作为实体抽取或在其间建立关系，避免'提到了'冒充'有关系'。
- [2026-09-19] 军事与地缘事件新闻中，行动所针对的国家/实体是故事的核心主体，必须抽为实体并与行动方建立关系（如 targets），不能只抽取行动方。
- [2026-09-19] 当机构与其子公司共同作为发起方时，founded_by 只挂一条（挂在母公司或子公司其一，或改由发起的研究者承载），不要对同一发起事件生成重复边。
- [2026-09-19] 区分『论文发表平台』（arXiv/期刊/会议，用 published_on）与『事件公开渠道』（博客/wiki/报告页面，用 references/documents），不要把事件公开渠道误作论文发表平台。
- [2026-09-20] 多个主体在同一句/段里被并列枚举（如'这些公司（OpenAI、Anthropic 等）'）只表示共同出现，不构成竞争或合作；仅在原文明确表述竞争/合作语义时才建立相应关系，否则删掉，不要把枚举句当证据。
- [2026-09-20] 原文明确列出多方争夺同一角色或市场（如'OpenAI、Google 与 Anthropic 都在争夺默认 AI 界面'）时，竞争关系必须覆盖所列全部主体且用争夺语作证据，不要漏掉其中一方，也不要拿与竞争无关的引文（如单方自身策略）作证。
- [2026-09-20] '×计划'、'×验证程序'（如 LSVP、评测计划）这类倡议/项目性质的主体不要标成 product，应使用 program/initiative（或 topic）等更贴切的类型。
- [2026-09-21] 呼吁/敦促类动作：source 敦促 target 去做某事时，不要用 targets 关系（会读成"指向/瞄准"），应选表达劝说/请求的关系类型如 calls_on，或不放边只保留在事件里。
- [2026-09-21] 只出现在假设句或未来设想里（"一旦 X 发布，连 A/B 也会扑进来"）而没有任何真实边的主体，不要抽成实体，剔除以免幽灵实体污染跨文章连通与计数。
- [2026-09-21] metrics 只能收可度量的数字参数，不要放"主角数/类别数"这类对原文的复述式凑数条目。
- [2026-09-22] 厂商自报的基准对比（尤其跨厂商 head-to-head 的 outperforms/cheaper_than）必须带"厂商声称、未经独立复核"的框架，不得当已证实事实写成断言；当双方厂商给出相反口径时要显式标注并降权。
- [2026-09-22] 生态/诉讼类新闻里关系要精确：法律纠纷（起诉）不能退化成泛化 targets 边，应使用诉讼类关系；原文标为"推进中/计划"的集成不得写成已完成 integrates。
- [2026-09-22] 版本号相邻的模型（如 Opus 5 与 5.5、GPT-5.6 与 GPT-6）是不同代际的不同实体，审计器报"疑似重复"时先读原文确认代际，确属不同模型则保留独立实体、不合并。
- [2026-09-23] 安全漏洞类新闻中，研究者与产品的关系应表达为披露/审计/诱导测试（disclosed_vulnerability_in、tests），不要用暗示敌意攻击的 targets 兜底。
- [2026-09-23] 区分方法/范式与工具：Tool-Calling 这类 agent 基线方法应标为 method/approach，不要标成 tool。
- [2026-09-23] 公司级事件（IPO、融资）的 subject 只用公司本身，CEO 的个人表态属于背景，放 why_it_matters/evidence，不要作为并列 participant。
- [2026-09-24] 当同一个规范名（如'美国'）在不同新闻中实际指代不同行为主体（联邦政府 vs 各州总检察长）甚至政治立场相反时，必须拆成两个独立实体并各自命名，不能共用一个规范名节点，否则会把互相矛盾的行为挂在同一主体上。
- [2026-09-24] 原文只是把 X 作为反例引用（'你不能买一台X…'）或作为打法借鉴来源（'借鉴了Y的打法'），或两家仅因同处一份评测排名各自升降（一家升入Gold、另一家退到Silver）时，都不构成 X/Y 之间的 compared_with 比较关系——仅在原文对双方做直接比较时才建立比较类边，被提及/被并列不产生关系。
