## 论文：字节跳动 Seed 提出 NSP（嵌套序列并行）——以共享 GPU 上的嵌套分组解决长尾变长序列训练的通信—负载均衡取舍达 1.48×
- source: arXiv
- date: 2026-09-22
- category: 论文
- url: https://arxiv.org/abs/2609.22755
- summary: 长上下文 LLM 训练面临"单一序列并行度无法同时适配长短序列"的两难——SP 度设小则少数长序列严重失衡，设大则占主导的短序列付出过高通信代价。字节跳动 Seed 提出的 NSP 通过把不同大小的 SP 组嵌套在共享 GPU 上、在单次训练迭代内共存，让长序列用大组、短序列用小组，只在该收的地方付出通信，端到端训练吞吐比静态 SP 最高提升 1.48×、比 FlexSP 最高 1.16×。
- detail: |
    论文的核心是一个"Planner–Executor"两段式设计：Planner 把允许的 SP 组约束成一棵 SP 树，每条根到叶路径描述可共享同一 GPU 的组；Executor 据此在真实系统里落地动态资源分配。由于序列长度高度异构（长尾分布），现有动态 SP 系统要么把 GPU 切成分立组从而重新引入跨组失衡，要么靠代价昂贵的 micro-batch 变通。NSP 的嵌套布局让异构长度的序列在共享算力上并行推进，通信开销只发生在真正需要 scale-up 的那部分。

    结果层面，NSP 在端到端吞吐上稳定优于静态 SP（最高 +48%）与 FlexSP（最高 +16%）。这篇工作的意义更多属于"训练系统工程"而非"新模型"：它直击长上下文训练里一个被 Benchmark 掩盖、却在百 K token 窗口普及后越来越痛的现实约束——当序列长度差异极大时，"一个 SP 度打天下"不再可行，而把通信与负载做成分层嵌套可同时消掉两种浪费。对部署长上下文模型训练的团队，它给出了"不买更多卡、先把并行度组织得更聪明"的一条可复用路径（ByteDance Seed 出品，代码与训练框架随论文公开）。

## 论文：Harness-Zero——北大/Google/HKUST 提出"agent harness 蒸馏"，把领域优化 harness 的行为压进模型权重
- source: arXiv
- date: 2026-09-22
- category: 论文
- url: https://arxiv.org/abs/2609.24974
- summary: agent 的最终能力同时取决于模型与"harness"（编排工具使用、管理上下文与状态、控制与环境交互的外部系统），但 harness 优化带来的收益在部署时仍绑在特定 harness 上。北大、Google 与 HKUST 的 Harness-Zero 把"领域或实例优化的 harness"当作训练期引导，把其行为蒸馏进模型权重，使收益在固定单一目标 harness 下依然存活——挑战在于两者动作空间与可用信息不同，优化的引导不能直接当监督信号。
- detail: |
    作者观察到：最好的 harness 随领域、实例与基础模型而变化，通用 agent 要么凑合一个次优的共享 harness，要么在一个不断膨胀的专门 harness 集合里做路由。Harness-Zero 的思路是"agent 作为 harness"式的蒸馏：把运营中调优好的脚手架行为迁移进训练好的权重，让部署时即便只用一套固定 harness 也能保有那部分增益。由于优化 harness 与目标 harness 在动作空间与信息可见度上不同，论文需要专门的方法把跨空间引导转化为可用于目标 harness 的监督。

    开放的 Github 仓库（metaevo-ai/harness-zero）与 9 月 22 日的日期让它成为当天 agent 研究里值得一读的增量之一：它把"scaffolding 也是一种可以蒸馏进权重的知识"这条思路正式化，和当下"scaffolding 工程是 agent 性能主流杠杆"的认知直接对照——潜台词是，今天大家靠外部系统堆出来的收益，未来有相当一部分可能被模型本身吸收，从而降低部署时对专门 harness 的依赖。
