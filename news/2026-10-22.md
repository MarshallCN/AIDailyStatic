- source: Semianalysis
- date: 2026-10-22

- summary: DeepSeek 在国庆前为 TileLang、DeepGEMM、DeepEP、FlashMLA 等六个仓库补上昇腾支持，SemiAnalysis 借机深潜昇腾 950PR 架构并拆解"华为有硬件没有前沿实验室、DeepSeek 有模型买不到算力"的共生关系。
- detail: |
    DeepSeek 于 9 月 30 日为 TileLang、DeepGEMM、DeepEP、TileKernels、FlashMLA、DeepSelect 六个仓库一并加入昇腾（Ascend）支持。SemiAnalysis 指出这桩"交换"靠任何一方都无法单独完成：华为虽有 Pangu 等自有模型，却没有前沿实验室能证明其芯片可以训练或推理顶尖模型；DeepSeek 有模型，却买不到它需要的算力。华为拿出硬件与原生软件栈，DeepSeek 带来工作负载与让硬件对其模型有用的工程能力，而交换的媒介正是内核编写语言——昇腾支持本身只是这层关系的可见产物。

    芯片侧，昇腾 950PR 存在大量变体（核心数、HBM 堆叠高度、缓存大小各异），原因不只是制造缺陷，也包括功率与性能的参差：华为与英伟达只对计算单元分档的做法不同，它把计算与内存捆绑成不同 SKU，弱内存配弱计算。对 950PR_9579（28 个 Cube 核、128 GiB HBM）的微基准显示，华为最优 GEMM 内核可达理论峰值的 99.7%，但绝对性能介于 A100 与 MI300X 之间；HBM 有效带宽在小消息尺寸下超过 H100，大消息的带宽利用率同样逼近 H100。芯片内的 Linx816 AICPU 与麒麟 9000S/9010 中核同源，适合 KV 元数据一类的短任务。

    软件侧，截至写作时六个仓库中只有 TileLang 真正可用——CANN 9.2.0 当时尚未发布且要求 C++20 编译器，HDK 要到 10 月 15 日才放出。关键在于昇腾 950 后端被并入 TileLang 主干，而非做成华为的独立适配器，带来原生编译、调度、同步与运行时集成；AutoSchedule 在 950PR 上对单算子最多可减少 40% 执行时间。昇腾架构也反向塑造了 DeepSeek 的数据布局：FlashMLA 为减少内存传输引擎的请求次数，把 KV 缓存的量化值与缩放因子合并到相邻区域。

    华为还正式加入了英伟达引领的大规模 scale-up 商业化：从 910 CloudMatrix384 到 950 SuperPod，跨机架紧密耦合加速器互连支撑 wideEP 扩展，EP16 dispatch/combine 基准跑在 URMA 之上——与 GB300 的单次融合调用不同，昇腾的 dispatch 是 pre/URMA/post 三个顺序算子。SemiAnalysis 的判读是：硬件相比 A100 落后约五年，但软件已站在前沿；到 2027-2028 年，在外部压力与内部建设完全国产化生态的推力下，DeepSeek 很可能主要运行在华为的栈上。

## 论文：LongZero——零外部数据，让大模型自我强化长上下文推理
- source: arXiv

- category: 论文
- url: https://arxiv.org/abs/2610.30132
- summary: 论文提出 LongZero：让大模型在零外部数据下用自提问题强化自身长上下文推理，无需人工标注、外部语料或更强的教师模型，在五个长上下文基准上超越用外部语料合成数据的强化学习基线。
- detail: |

    在两个 LLM、五个长上下文推理基准上与"用外部语料合成数据做 RL"的基线相比，LongZero 均取得更优表现并能泛化到真实任务。作者认为这为"无数据长上下文 RL"提供了一条可行路径——当最强模型已无外部教师可用时，自我生成训练信号是少数仍在扩展方向的训练范式。

## 论文：P2NPCBench——P 与 NP 完全问题配对，暴露模型"记忆而非推理"
- source: arXiv
- date: 2026-10-22
- category: 论文
- url: https://arxiv.org/abs/2610.30103
- summary: 论文提出 P2NPCBench：给每个 NP 完全问题配上只差一个结构细节的 P 类孪生题，12 个模型在 NPC 侧显著更低（35.4% 对 63.8%），提示部分差距来自对教科书表述的熟悉而非复杂度本身。
- detail: |
    许多 NP 完全（NPC）问题有一个只在单一结构细节上不同的多项式时间（P）孪生问题——例如三着色对二着色。能在推理而非回忆的模型应当识别出这道分界线，但现有基准要么固定题目措辞、要么忽略复杂度类别，无法把两者分开。论文用对抗式多智能体框架 AgentGAN 构造 P2NPCBench：生成器不断改写题目直至一组冻结的代码模型无法通过，同时可执行合法性门保证每次改写保持答案与复杂度类别不变，产出 2114 道硬化题与人工核验的参考解答。

    评测 12 个专有与开源模型：所有模型在 NPC 题上的得分都低于 P 孪生题（35.4% 对 63.8%），95.1% 的模型-家族配对在 NPC 侧失败更多；把时限放宽十倍也只把 NPC 准确率从 28.5% 提到 31.9%，说明失败源于错误或崩溃的程序而非速度。更关键的是，硬化把类别差距从 24.8 分收窄到 14.6 分——说明模型表现出的"P/NPC 差距"有相当一部分只是对教科书题面的熟悉，而非真正的复杂度理解。

## OpenAI 推出 Decisions API：基于 GPT-6 Luna 的"快速聚焦"决策端点
- source: OpenAI
- date: 2026-10-22
- category: 应用/产业
- url: https://openai.com/index/decisions-api
- summary: OpenAI 将基于 GPT-6 Luna 的 Decisions API 全面可用：它把 Luna 的智能聚焦在有限答案的问题上，从文本、图像与结构化输入做近实时决策，比走 Responses API 快最多 10 倍，且只按输入 token 计费。
- detail: |
    OpenAI 宣布 Decisions API 全面可用。应用与 agent 在流程中要做大量小决策——分类输入、路由请求、决定下一步动作——单个都很简单，但规模化后延迟与成本累积。Decisions API 内置 GPT-6 Luna，专为"有界答案"设计，开发者定义问题与允许的答案，提供文本、图像或原生 JSON 上下文，返回概率（predicate）、选项（choice）或评分（score）三类答案之一。相比 Responses API 上调用 Luna，速度提升最多 10 倍。

    定价突出"只按输入计费"：每百万输入 token 0.1 美元，缓存输入 0.01 美元，没有输出 token 费用；支持美欧推理驻留与零数据保留。GA 版还加入原生 GPT-Live 集成（语音会话中做表情/路由等实时决策）、复用上下文的 prompt 缓存，单请求可提至 400 个问题。OpenAI 内部 Dots 团队用它降低响应时间，通讯团队用它给媒体报道做主题打分。它代表模型层的一个新分化方向：把"概率式生成"与"确定性裁决"分开成两种 API 形态，决策类负载不再需要为完整文本生成付费。
