Q1: 这篇论文试图解决什么问题？

这篇论文旨在解决**长程智能体（long-horizon agents）的执行可靠性问题**，即：即使底层基础模型具备解决各个局部子步骤的能力，完整的任务执行仍可能失败。 具体而言，论文聚焦于以下核心问题与解决路径： ### 1. 长程执行中的系统性失败模式 论文识别了导致长程任务失败的若干关键执行层缺陷，包括： - **状态丢失（mutable-state ambiguity）**：智能体难以从仅追加的历史记录中重建当前任务状态（如已完成目标、待处理依赖、失败尝试等）； - **控制信号稀释（control-signal dilution）**：随着执行轨迹增长，原本紧凑的计划与完成标准被淹没在海量的命令、观测与修复记录中； - **程序记忆缺失（procedural-memory gap）**：智能体在某次运行中正确诊断了失败原因，但无法在后续遇到相同风险时重新激活该经验； - **程序合规性不足（procedural-compliance gap）**：已知正确程序在执行过程中未被完整遵循，或关键检查被跳过； - **过早终止**：智能体在交付物被可验证地完成之前就停止执行。 ### 2. Harness Scaling 的核心命题 论文提出一个与模型缩放正交的视角——**Harness Scaling（执行系统缩放）**： - **核心问题**：有多少看似的“模型失败”实际上是维持状态、约束执行、验证进度和从错误中恢复的** surrounding control layer（ surrounding 控制层）** 的失败？ - **核心假设**：通过系统性改进智能体外部的运行时控制层（而非修改模型权重），可以将模型已有的固有能力更可靠地转化为完整、可验证的完成结果。 ### 3. 分层的实证检验框架 论文将上述问题进一步分解为四个逐层递进的实证检验： - **固定模型提升**：更好的 harness 能否在不改变权重的情况下提升单一模型的表现？ - **冻结跨代迁移**：为一个模型开发的 harness 能否不经修改直接迁移到同家族的下一代模型？ - **适配跨提供者迁移**： harness 的开发原则与结构能否低成本适配到不同提供者的模型？ - **跨任务泛化**：控制边界的抽象方法能否在不同任务族间保持有效？ ### 4. StateM 的运行时解决方案 为具体解决上述问题，论文引入 **StateM**，一个面向 CLI 智能体的原生运行时，其设计直接回应前述失败模式： - 将执行组织为**耐久的状态边界**，进入状态时刷新阶段相关的控制上下文与指令； - 通过**显式检查（checked transitions）**约束阶段间的转换，防止未完成的工作被静默移交； - 利用**版本化的运行手册（versioned runbook）**将事后总结的失败教训转化为可执行、可审计的先决条件与程序实践，填补跨运行的程序记忆缺口。 简言之，该论文试图论证并验证：**长程智能体的许多失败并非源于模型能力不足，而是源于缺乏一个显式、可检查、可积累执行经验的外部控制层；通过系统化地缩放这一 harness 层，可以在不修改模型的情况下，获得相当于甚至超越模型代际升级的系统性能提升。**

Q2: 有哪些相关研究？

论文将相关研究归纳为四条主要脉络，并在其中定位 StateM 的贡献。以下按研究领域分类梳理： ### 1. 长程规划与智能体执行（Planning and Long-Horizon Agent Execution） 该领域关注智能体如何在长时间跨度的任务中保持计划并执行到位。 - **计划偏离与提前终止**：现有研究表明，当前智能体经常偏离其计划、遗漏必要步骤或在未满足原始完成标准时终止（Liu et al., 2026）。 - **编排的代价**：Dennis et al. (2026) 发现，在某些情境下，将完整程序直接置于上下文中让强模型执行，反而比重度编排的节点化流程表现更好。这揭示了“控制强度”与“推理自主性”之间的张力，也是 StateM 试图平衡的出发点。 - **相关基准**：包括评估工具-智能体-用户交互的 $\tau$-bench（Yao et al., 2024）、双控环境的 $\tau^2$-bench（Barres et al., 2025），以及长程软件工程任务基准 SWE-bench Pro（Deng et al., 2025）。 ### 2. 有状态与基于图的编排（Stateful and Graph-Based Orchestration） 这类系统通过显式的工作流状态、持久化、条件路由和恢复机制来增强可靠性。 - **StateFlow**（Wu et al., 2024）：利用显式状态与状态转换驱动执行，证明状态化执行可改善任务 grounding 与失败恢复。 - **LangGraph**（Wang and Duan, 2024）：提供持久状态、条件边、检查点、中断恢复与人机协作能力，代表了“开发者指定控制器”的图编排范式。 - **与 StateM 的区别**：上述系统通常将智能体置于开发者编写的外部控制图内部；StateM 则保持通用 CLI 智能体作为首要执行者，让智能体通过常规工具环境直接操作控制层。 ### 3. 长程智能体与智能体老化（Long-Horizon Agents and Agent Aging） 该方向关注跨会话甚至部署周期中的可靠性退化。 - **AgingBench**（Zhu et al., 2026）：提出即使模型权重冻结，部署后的智能体仍会随时间因记忆压缩、干扰、修订和维护而“老化”。该工作进一步指出，部分纵向失败需要**显式状态表示**而非仅靠追加文本记忆，并研究了类型化状态叠加与运行时控制干预。这与 StateM 的外部化状态表示形成互补。 ### 4. 工具调整与自我改进（Harness Adaptation and Self-Improvement） 近年来，越来越多的研究表明智能体性能强烈依赖于其运行时 harness，且 harness 本身可被优化。 - **Agentic Harness Engineering**（Lin et al., 2026; Gu, 2026）：利用执行可观测性，从轨迹反馈中自动演化编码智能体的工具、中间件、提示与记忆。 - **Life-Harness**（Xu et al., 2026）：将重复失败转化为对环境契约、程序技能、动作实现与轨迹调控的可复用干预，并在冻结后用于留出评估。 - **Self-Harness**（Zhang et al., 2026）：让智能体挖掘自身弱点，提出 harness 修改，并通过回归感知验证进行提升。 - **Better Harnesses, Smaller Models**（Yang et al., 2026）：研究自动化 harness 适配，使低成本模型能够恢复大模型的大部分性能。 - **StateM 的定位**：与上述方法在“超智能体（hyper-agent）优化循环”上相近，但 StateM 的核心差异在于被优化的制品是一个**显式的、机器可操作的、智能体原生的状态机运行手册（runbook）**，可同时作为运行时控制、审计表面与优化搜索空间。 ### 5. 通用 CLI 智能体与软控制（CLI Agents, Soft Plans, and User Control） - **Codex / Claude Code** 等通用 CLI 智能体保留了广泛的工具选择与迭代推理自主权，但其计划、待办清单、规则文件与钩子通常不构成统一的、具有转换感知能力的控制面。 - StateM 将这类“软控制片段”整合为一份共享的、可审计的运行手册，使人类监督者能够编辑与智能体和运行时相同的控制制品，而非只能向对话历史中追加自然语言纠正。 ### 6. 评估基准（Evaluation Benchmarks） 论文实验涉及两项主要基准： - **Terminal-Bench 2.1**（Merrill et al., 2026）：包含 89 项基于命令行界面的困难现实任务，用于测试 harness 在质量与成本前沿的表现。 - **BusinessBench**（Yang et al., 2026）：包含七个任务族，用于测试 harness 在异构任务间的泛化能力。

Q3: 论文如何解决这个问题？

论文通过**Harness Scaling（执行系统缩放）**与**StateM（智能体原生有状态运行时）**的结合，在不修改模型权重的前提下解决长程执行可靠性问题。其核心解决路径可分为设计原则、运行时机制、缺口填补与持续优化四个层面。 --- ### 1. 核心策略：Harness Scaling 论文将问题归因于**控制层（harness）**的缺陷，而非基础模型能力不足。解决思路是系统性地改进维护状态、约束执行、验证进度和支持恢复的外部运行系统，将模型已有的固有能力更可靠地转化为完整的任务交付。 --- ### 2. StateM 的运行时架构 StateM 是一个轻量级、基于 YAML 运行手册（runbook）的状态机运行时，智能体通过常规 CLI 命令直接操作该控制层。运行手册定义了状态、允许转换、阶段局部指令、钩子（hooks）、检查（checks）与恢复规则。 #### 2.1 状态作为上下文与契约边界 每个状态同时承担两种角色： - **上下文边界（Context Boundary）**：进入状态时，`in_hook` 刷新该阶段相关的控制信号、持久化任务进度与局部义务，修复长轨迹中的控制信号稀释问题。 - **契约边界（Contract Boundary）**：`before_transfer` 模块规定了离开状态前必须满足的显式退出条件。状态体（state body）内保留智能体的开放推理与工具调用自主权，但跨阶段推进必须经过检查。 #### 2.2 运行手册的形式化结构 运行手册被形式化为： $$\mathcal{B} = (\mathcal{S}, s_0, \mathcal{S}_T, \mathcal{E}, \Phi)$$ 其中 $\mathcal{S}$ 为状态集合，$s_0$ 为初始状态，$\mathcal{S}_T \subseteq \mathcal{S}$ 为终止状态集合，$\mathcal{E} \subseteq \mathcal{S} \times \mathcal{S}$ 为允许转换，$\Phi(s)$ 包含状态局部的提示、钩子与检查配置。 #### 2.3 受检转换协议（Checked Transition Protocol） 所有阶段变更通过核心操作 `goto TARGET` 执行，遵循六步协议： 1. 验证请求边是否存在于当前状态到目标状态之间； 2. 评估当前状态的 `before_transfer` 检查； 3. 执行当前状态的持久化或 `out_hook`； 4. 评估边守卫（edge guards）与边级传输钩子； 5. 仅在所有前置步骤通过后，提交目标状态并追加转换事件到历史； 6. 创建目标状态条目并执行其 `in_hook`。 若任一前置检查失败，运行保留在源状态并记录失败，智能体可在修复后重试，从而防止未完成的交接被静默提交。 #### 2.4 持久化运行状态与恢复 每次执行拥有独立的运行时记录，包括当前状态、状态进入标识、转换历史、钩子与检查结果、时间戳及证据文件引用。在进程重启、上下文刷新或模型侧压缩后，智能体可通过查询 StateM 恢复其阶段和义务，而非仅从追加式的终端历史中重建任务状态。 #### 2.5 共享控制与可审计性 运行手册是智能体与用户**共享的、可版本化的工作空间制品**。用户可编辑和审计该制品，智能体可在授权范围内注册运行时的动态检查。此外，StateM 支持与宿主级 `stop-hook` 集成：当宿主收到停止请求时，钩子检查当前是否处于非终止状态或未满足外部依赖，若工作尚未完成则请求继续执行，减少过早终止。 --- ### 3. 针对三类执行缺口的控制映射 StateM 为三类具体的执行失败提供了独立的控制点： | 失败缺口 | StateM 控制机制 | 作用 | |---|---|---| | **Epistemic Gap（知识缺口）** | 状态局部 `in_hook` | 在关键阶段重新激活领域知识、工具指引与任务上下文，确保决策点具备必要信息 | | **Procedural-Compliance Gap（程序合规缺口）** | `before_transfer` 检查、转换守卫与证据要求 | 阻止已知程序被跳过或不完整执行，将运行保持在可修复的源状态 | | **Procedural-Memory Gap（程序记忆缺口）** | 版本化的运行手册实践（prompts, checks, recovery rules） | 将某次运行的失败教训编码为持久、可执行的预条件，使后续独立运行自动复用 | --- ### 4. 失败驱动的 Harness 优化循环 论文将单次执行经验转化为系统级可靠性的机制称为 **failure-driven harness optimization**： - **执行与观察**：运行当前版本的控制配置，收集失败轨迹与验证器反馈； - **归因与抽象**：将失败归类为缺失上下文、无效转换、弱检查、过早交接、恢复失效等控制层缺陷，并抽象为可复用的执行课程； - **编码与验证**：由工作智能体或超智能体（hyper-agent）提出对状态边界、提示、钩子、检查、恢复规则与实践激活条件的修改；经过回归测试后纳入新版本运行手册； - **冻结与迁移**：优化后的配置可被冻结并跨模型代际直接使用（如 GPT-5.5 运行手册零成本迁移至 GPT-5.6），或作为结构模板低成本适配至其他提供者（如 DeepSeek-V4-Flash）。 该循环的关键约束是**选择性记忆**：并非所有失败轨迹都直接转化为规则，而是仅保留那些针对“关键执行边界”的、经抽象后具备泛化潜力的控制，以避免控制漂移与负迁移。 --- ### 5. 分层迁移以扩展适用范围 针对不同距离的模型与任务，论文采用分层迁移策略，而非假设单一配置普遍适用： - **同模型/同家族冻结迁移**：具体的状态、检查、路由规则可完整复用； - **跨提供者适配迁移**：保留通用运行时、高层结构与开发原则，仅针对新模型的残余失败分布调整具体实践（如 DeepSeek 适配成本低于 $38）； - **跨任务族泛化**：将控制绑定到最小必要的不变量（如数值精度、副作用闭包、实体一致性），仅在任务族共享相关执行结构时才施加干预，否则选择弃权。

Q4: 论文做了哪些实验？

论文围绕**质量前沿（quality frontier）**与**成本前沿（cost frontier）**两条主线，在 **Terminal-Bench 2.1** 和 **BusinessBench** 两个基准上开展了系统性实验。实验覆盖固定模型提升、冻结跨代迁移、跨提供者适配迁移以及跨任务族泛化四个层次。 --- ### 1. 实验设定与共用配置 - **基准测试**： - **Terminal-Bench 2.1**：89 项基于命令行的长程现实任务，每项运行 5 个 trial，共 445 个 trial。主指标为 trial 级成功率，同时报告 5-trial 任务覆盖（即 Pass@5）。 - **BusinessBench**：7 个任务族共 477 个实例，测试 harness 在异构业务工作流中的泛化性。 - **被测模型**：GPT-5.5 xhigh、GPT-5.6 Sol xhigh、GPT-5.6 Luna、DeepSeek-V4-Flash。 - **评估原则**：开发阶段允许基于可见任务语义与执行反馈优化 harness；冻结评估阶段禁止利用目标模型结果修改 runbook。 --- ### 2. Terminal-Bench 2.1：质量前沿与成本前沿 #### 2.1 固定模型提升（Same Model, Better Harness） 使用 **GPT-5.5 xhigh** 隔离 harness 的净效应： - 基线：$83.1\%$ - + StateM：$92.1\%$，提升 $+9.0$ 个百分点 - 5-trial 任务覆盖：$88/89$（$98.9\%$） - 该结果数值上超过了 GPT-5.6 Sol ultra 的参考值 $91.9\%$，表明 harness 改进可产生相当于模型代际升级的系统级增益。 #### 2.2 冻结跨代迁移（Frozen Transfer within GPT Family） 将在 GPT-5.5 上开发并冻结的 runbook **零修改**应用于 GPT-5.6： - **GPT-5.6 Sol xhigh**： - 基线：$84.9\%$ - + frozen StateM：$424/445 = 95.28\%$（报告为 $95.3\%$），提升 $+10.4$ 个百分点 - 5-trial 任务覆盖：$89/89$（每项任务至少成功一次） - **GPT-5.6 Luna**： - 基线：$76.7\%$ - + frozen StateM：$85.4\%$，提升 $+8.7$ 个百分点 - 该结果数值上超过了 GPT-5.6 Sol xhigh 的基线 $84.9\%$ #### 2.3 跨提供者适配迁移（Adapted Transfer to DeepSeek） 测试 runbook 结构、运行时与开发原则在 **DeepSeek-V4-Flash** 上的可迁移性： - 基线：$82.7\%$ - 直接冻结迁移（GPT profile 零修改）：$82.0\%$（略有下降，说明具体实践不能跨提供者直接复用） - 基于相同 runtime/结构/原则进行**低成本适配**后： - 标准超时、全量 89 任务：$392/445 = 88.09\%$ - 88 任务共同核心（排除对延迟敏感的 gpt2-codegolf）：$392/440 = 89.09\%$ - 描述性聚合（仅对 gpt2-codegolf 延长超时）：$(392+3)/445 = 395/445 = 88.76\%$，四舍五入为 $88.8\%$，与报告的 GPT-5.6 Sol max 分值对齐 #### 2.4 成本前沿分析（Cost Frontier） DeepSeek 侧的实际 API 支出： - 最终评估产生报告分数的 API 费用：约 $\$15.20$ - 提供者特定的 profile 适配费用：$\$37.02$ - 全部记录支出（适配 + 评估）：$\$52.22$ - 作为对比，公开的 GPT-5.6 Sol max 提交报告模型成本为 $\$574.68$；论文中 GPT-5.6 Sol xhigh + StateM 的提交报告成本为 $\$1,062.95$ - 成本效率：最终证据成本约为对比提交的 $1/37.8$；总支出约为 $1/11$ --- ### 3. BusinessBench：任务侧泛化 在 **GPT-5.6 Luna** 上评估 harness 方法在异构任务族间的适用性。7 个任务族中，对 6 个族应用 StateM，**attendance-payroll** 族主动弃权。 #### 3.1 冻结一次性留出评估（Frozen One-Shot） - **Family macro**（等权重族平均）：$84.67\% \to 85.22\%$（$+0.55$） - **Instance micro**（实例加权平均）：$84.44\% \to 85.78\%$（$+1.34$） - **开发集**：$86.07\% \to 91.71\%$（$+5.64$） - **全部受试实例**：$84.76\% \to 88.72\%$（$+3.96$） #### 3.2 机制匹配子组的显著增益 两个执行边界清晰的族表现出大幅改进： - **Budget Approval**：$62.91\% \to 75.12\%$（$+12.21$） - **Machine Operating**：$90.79\% \to 100.00\%$（$+9.21$） - 两族合计 macro 平均：$71.91\% \to 81.94\%$（$+10.04$） #### 3.3 负迁移与边界错配 首次冻结评估中出现性能下降，归因于控制边界与任务不匹配： - **RefactorBench**：$80.56\% \to 77.78\%$（$-2.78$） - **WooCommerce Stock**：$92.59\% \to 88.89\%$（$-3.70$） #### 3.4 评估后诊断验证 针对负迁移族进行选择性 profile 修正后的匹配重运行

Q5: 有什么可以进一步探索的点？

基于论文的局限性与讨论章节，以下是可以进一步探索的研究方向： --- ### 1. 多智能体运行时与角色隔离 论文当前聚焦于单智能体控制流，但在讨论中指出，**状态、上下文与权限的分离原则同样适用于多智能体系统**。值得探索的方向包括： - 如何通过角色隔离（role-specific read/write permissions）为不同智能体提供独立的决策上下文，防止单一智能体在自身历史决策形成的偏见中持续推理； - 多智能体间的状态共享、协调协议与权限设计，特别是在审查（review）、验证（verification）与委派（delegation）场景中的应用； - 如何在保持各自统一推理循环的同时，通过 StateM 式的共享运行手册实现跨智能体的可审计控制。 --- ### 2. 与纵向智能体老化（Agent Aging）的结合 论文将 StateM 定位为与 **AgingBench** 互补：AgingBench 诊断跨会话的寿命期退化机制（压缩老化、干扰老化、修订老化、维护老化），而 StateM 解决单次长程任务内的程序状态管理。未来可探索： - 将 AgingBench 的寿命期诊断与 StateM 运行手册的跨会话自适应演化相结合； - 如何利用 StateM 的显式状态表示来缓解 AgingBench 中识别的“修订老化”与“维护老化”问题； - 长期部署中，运行手册版本如何与记忆系统的压缩和检索策略协同演化。 --- ### 3. 自动化且可靠的经验抽象机制 论文反复强调 **“选择性记忆”** 的重要性——并非所有失败 traces 都应转化为持久控制。当前流程依赖超智能体或人类审核来抽象可复用的实践。进一步探索包括： - 开发更鲁棒的超智能体方法，自动判断某次失败归因应成为全局规则、局部检查还是被丢弃； - 建立机制防止将评估器特定偏好（evaluator-specific conventions）或事后默认参数错误地编码为通用实践； - 研究控制规则的“有效期”与淘汰机制，避免运行手册随时间无限膨胀。 --- ### 4. 异构任务间的控制边界自动识别 BusinessBench 实验表明，**增益高度依赖于控制边界与任务执行结构的匹配**。当边界错配时，会出现负迁移。未来工作可包括： - 自动识别不同任务族中“容易漂移且后果严重”的执行边界，而非依赖人工设计阶段； - 研究任务结构特征（如副作用模式、数值推导链、跨系统实体依赖）与最优控制粒度之间的对应关系； - 构建元学习方法，使 harness 能够根据新任务族的少量样本推断出应施加控制的关键相位。 --- ### 5. 在更广泛的模型与基准上验证 当前实验主要覆盖 OpenAI GPT-5.5/5.6 系列与 DeepSeek-V4-Flash，基准集中于 Terminal-Bench 2.1 与 BusinessBench。扩展验证方向包括： - 在其他强基座模型（如 Claude 系列、Gemini、Llama 等）上测试 StateM 运行时与开发方法的可迁移性； - 在更长程、更复杂的软件工程基准（如 SWE-bench Pro）上评估状态化控制对代码迁移、多仓库重构等任务的效果； - 探索 StateM 在需要实时人机协作（human-in-the-loop）场景中的适用性。 --- ### 6. 增强检查机制的语义强度 StateM 当前支持的 `llm_review` 和 `checklist` 检查本质上仍属于**语义性自证**，不具备独立可复现的确定性。未来可探索： - 将轻量级形式化方法（如符号执行、类型检查、契约验证）嵌入 `before_transfer` 环节，替代或增强基于 LLM 的审查； - 开发更严格的外部验证器（external verifiers），使关键转换条件（如服务就绪、数值守恒、实体一致性）获得独立于模型声明的可复现证据； - 研究“软默认”与“硬门控”之间的动态平衡，在保证安全性的同时不过度限制智能体在开放域中的推理灵活性。 --- ### 7. Harness 缩放与模型缩放的系统性权衡边界 论文展示了通过 harness 改进使廉价模型接近昂贵模型性能的案例，但尚未系统刻画： - **哪些能力缺口可被 harness 弥补，哪些必须依赖模型本身的能力提升**（例如复杂推理、领域知识、创造力）； - 在不同任务复杂度、错误代价和延迟约束下，最优的“模型能力 + harness 成本”组合是什么； - 建立理论或实证框架，量化 harness 改进与模型代际升级之间的等效关系（harness-model equivalence）。 --- ### 8. 运行时的自主演化与安全自修改 当前 StateM 允许智能体在授权下注册运行时动态检查，但基础运行手册的修改仍受控。进一步方向包括： - 设计更精细的权限边界，使智能体能够安全地提议并测试运行手册变更，同时保证核心不变量（invariants）不被削弱； - 研究运行手册的“沙盒化”更新机制：允许智能体在隔离版本中试验新规则，经回归验证后再合并到主版本； - 探索停止钩子（stop hooks）与资源限制（时间、预算、重试次数）的更优联合策略，以在避免过早终止的同时保证可接受的总体成本。 --- ### 9. 控制信号稀释的量化分析 论文将 **control-signal dilution** 作为操作假设提出，但未提供基于注意力机制或上下文压缩的定量实证。未来可探索： - 在长程执行轨迹中，测量计划 token 与执行 token 在模型上下文中的有效注意力权重变化； - 量化上下文长度、历史压缩率与关键指令召回率之间的关系，为 StateM 状态刷新的频率与粒度提供数据驱动的设计依据。

Q6: 总结一下论文的主要内容

该论文围绕**Harness Scaling（执行系统缩放）**这一核心命题，提出长程智能体（long-horizon agents）的大量失败并非源于基础模型能力不足，而是源于执行控制层（harness）在状态维护、上下文刷新与转换约束上的缺陷。论文引入 **StateM**，一个智能体原生的有状态运行时，通过显式状态边界、受检转换与版本化运行手册，在不修改模型权重的情况下，将模型的局部能力可靠地转化为完整的任务交付。 --- ### 1. 核心问题：长程执行中的控制层失效 长程智能体常出现一种 revealing failure mode：底层模型能够解决各个局部子步骤，但完整运行仍可能失败。论文将根因归结为两类操作性压力： - **控制信号稀释（control-signal dilution）**：随着执行轨迹增长，原本紧凑的计划与完成标准被淹没在海量的命令、观测与修复记录中； - **可变状态模糊（mutable-state ambiguity）**：当前任务状态（已完成目标、待处理依赖、失败尝试）必须从仅追加的历史中重建，而非从权威的当前状态中读取。 这些压力导致三类执行缺口： - **认知缺口（epistemic gaps）**：决策点缺乏必要的领域知识或上下文； - **程序记忆缺口（procedural-memory gaps）**：某次运行中获得的教训无法在后续运行中被重新激活； - **程序合规缺口（procedural-compliance gaps）**：已知的正确程序未被完整执行或关键检查被跳过。 --- ### 2. StateM：智能体原生有状态运行时 StateM 的核心是一个轻量级、基于 YAML 的运行手册（runbook），定义了状态集合 $\mathcal{S}$、初始状态 $s_0$、终止状态集合 $\mathcal{S}_T \subseteq \mathcal{S}$、允许转换边 $\mathcal{E} \subseteq \mathcal{S} \times \mathcal{S}$，以及状态规范 $\Phi(s)$（包含阶段局部提示、钩子与检查）。 其设计遵循三项原则： - **状态作为上下文与契约边界**：进入状态时，`in_hook` 刷新该阶段相关的控制信号与持久进度；离开状态时，`before_transfer` 检查必须全部通过，方可提交转换。 - **智能体保留执行自主权**：在每个状态体内，通用 CLI 智能体仍拥有开放的工具选择与推理空间，避免过度编排导致的推理碎片化。 - **共享可审计的控制面**：运行手册是工作空间中的普通制品，智能体通过常规 CLI 命令操作它，用户可直接编辑、审计与版本化同一文件。 转换协议采用六步 `goto` 流程：验证边存在 $\to$ 评估源状态退出检查 $\to$ 执行持久化钩子 $\to$ 评估边守卫 $\to$ 提交目标状态 $\to$ 执行目标状态进入钩子。任何前置检查失败都会将运行保留在源状态，允许修复后重试。 --- ### 3. 失败驱动的 Harness 优化 StateM 支持将执行失败转化为版本化的程序实践（practices）。通过“执行 $\to$ 观察 $\to$ 归因 $\to$ 抽象 $\to$ 编码 $\to$ 验证”的闭环，选定的教训被固化为运行手册中的状态边界、提示、检查或恢复规则，从而填补跨运行的程序记忆缺口。关键在于**选择性记忆**：仅将针对关键执行边界的、经抽象后具备泛化潜力的控制持久化，避免控制漂移。 --- ### 4. 实验验证：质量前沿、成本前沿与迁移层次 实验在 **Terminal-Bench 2.1**（89 项任务，445 个 trial）和 **BusinessBench**（7 个任务族，477 个实例）上展开，涵盖四个迁移层级： #### 4.1 固定模型提升（质量前沿） - **GPT-5.5 xhigh**：基线 $83.1\%$ $\to$ StateM $92.1\%$（$+9.0$ 点），5-trial 任务覆盖 $88/89$。 - **GPT-5.6 Sol xhigh**：基线 $84.9\%$ $\to$ 冻结迁移 StateM $424/445 = 95.28\%$（$+10.4$ 点），覆盖 $89/89$。 - **GPT-5.6 Luna**：基线 $76.7\%$ $\to$ 冻结迁移 StateM $85.4\%$（$+8.7$ 点），数值上超过 GPT-5.6 Sol xhigh 基线。 #### 4.2 跨提供者适配迁移（成本前沿） - **DeepSeek-V4-Flash**：直接冻结迁移效果不佳（$82.7\% \to 82.0\%$），但基于相同运行时与结构进行低成本适配后： - 标准超时全量 89 任务：$392/445 = 88.09\%$； - 88 任务共同核心：$392/440 = 89.09\%$； - 描述性聚合（仅延长 gpt2-codegolf 超时）：$395/445 = 88.76\%$，与 GPT-5.6 Sol max 报告的 $88.8\%$ 对齐。 - **成本**：最终评估证据的 API 支出约 $\$15.20$；全部适配与评估记录支出 $\$52.22$。相比之下，公开的 GPT-5.6 Sol max 提交报告模型成本为 $\$574.68$。 #### 4.3 跨任务族泛化 在 **BusinessBench** 上，6 个受试族的冻结一次性评估显示： - Family macro 平均：$84.67\% \to 85.22\%$（$+0.55$）； - Instance micro 平均：$84.44\% \to 85.78\%$（$+1.34$）； - 机制匹配子组（Budget Approval + Machine Operating）：$71.91\% \to 81.94\%$（$+10.04$）。 同时观察到**负迁移**（RefactorBench、WooCommerce Stock 初次下降），归因于控制边界与任务结构错配；经针对性修正后，性能恢复并提升。这表明：控制 profile 的泛化遵循**机制匹配原则**，而非任务多样性原则。 --- ### 5. 核心结论 论文得出以下主要结论： - **Harness Scaling 是与模型缩放正交的能力维度**。在观测设置中，harness 改进对完成率的提升远大于同代际模型升级带来的增益。 - **迁移具有层次性**：具体实践可冻结迁移至同家族模型；运行时结构与开发原则可低成本适配至跨提供者模型；控制边界抽象方法可跨任务族泛化，但仅在共享相关执行结构时生效。 - **执行可靠性取决于三项控制的协同**：状态局部上下文填补认知缺口，受检转换填补合规缺口，版本化实践填补记忆缺口。 StateM 并未声称使所有模型在所有任务上 universally stronger，而是将执行失败转化为可检查、可积累的外部控制，使经验能够以显式、可执行的形式持久化，而无需重新训练模型权重。核心代码与部分运行时案例已开源。
