Q1: 这篇论文试图解决什么问题？

这篇论文试图解决**大规模语言模型（LLM）Agent 在持续处理同类型任务流时，控制逻辑被反复重建所导致的效率低下与成本高昂**问题。具体可从以下三个层面理解： ### 1. 核心问题：重复控制决策的在线重建 在标准 Agent 框架（Harness）中，处理每一个任务实例时，模型都需要在上下文里重新推理并生成相同的控制行为——例如查询细化、观察过滤、进度验证、错误恢复以及终止判断。尽管任务目标与观察结果随实例变化，但周围的控制结构往往是重复出现的。这种**“每次任务都重新推理控制”**的模式带来三重代价： - **推理调用冗余**：相同的控制决策被反复委托给 LLM； - **上下文膨胀**：执行历史、提示与观察不断累积，增加输入长度； - **部署成本高昂**：尤其在资源受限场景（如移动设备）下，小型模型难以承受高频在线推理。 ### 2. 关键科学问题：如何将重复控制外化为可重用代码 论文围绕一个核心命题展开——**能否利用任务反馈将反复出现的控制逻辑转化为持久、可执行的重用代码，同时仅将 LLM 保留用于任务特定的语义推理**。这要求解决三个技术挑战： - **代码与模型调用的边界判定**：哪些行为应固化为确定性代码（如解析、校验、状态更新），哪些必须保留为 LLM 调用（如语义理解、模糊比较、答案生成），以避免规则过于脆弱； - **增量式程序优化**：随着 Harness 不断积累能力，如何避免优化器在每一步都处理整个程序，而是将失败定位到有限的局部代码表面，使搜索空间与程序总规模解耦； - **防止退化与脆弱性**：针对某次失败的修复可能编码实例特定规则，或损害已习得的早期行为，需要机制确保新增能力具有跨任务迁移性且不引发回归。 ### 3. 目标范式：从“无策略脚手架”生长出可复用的专家 Agent 论文提出的 **Growing Harness** 范式旨在满足三项要求： - **重用性**：从训练任务中习得的行为应泛化到同分布的未见任务； - **上下文高效执行**：将例行控制移出模型上下文，减少 LLM 调用与上下文压力； - **低先验承诺**：无需在初始化时预设完整的控制器（如 ReAct 式工具调用循环），而是从一个仅暴露固定模型与工具接口、但**不编码任何任务求解策略**的空脚手架出发，让可执行结构完全通过任务反馈自适应生长。 最终目标是实现**“增长 Harness，而非增长上下文”**：将可重复的控制结构持久化为低成本的代码路径，仅在需要语义判断时调用 LLM，从而构建能在小型部署模型上保持高效且可复用的专业化 Agent。

Q2: 有哪些相关研究？

该论文在第2节（Related Work）中系统梳理了五个相关研究方向，各方向的代表性工作及其与本文的核心区别如下： ### 1. 工具使用 Agent 的推理时控制（Inference-time control） 此类研究关注如何围绕 LLM 组织推理、工具调用与观察处理。 - **代表性工作**：ReAct（推理与行动交错）、Self-Ask（将问题分解为显式追问）、IRCoT（检索与多步推理交替）、Reflexion（将早期尝试的反馈带入后续执行）。 - **与本文的区别**：这些方法在部署前即固定了控制循环结构，控制决策以文本历史形式存在，需要模型在每一步重新计算。本文则探索**控制结构本身能否随任务反馈演化**，使后续任务直接复用代码而非重复推理。 ### 2. 跨任务的持久化经验（Persistent experience across tasks） 此类研究关注如何将早期任务经验迁移到后期任务。 - **文本经验复用**：ExpeL、Agent Workflow Memory 等通过存储自然语言洞察、示例或工作流供后续检索。 - **可执行技能蒸馏**：Voyager、LATM、CRAFT 等将经验封装为可重用的代码技能或工具集。 - **与本文的区别**：文本经验需要在线检索并在模型上下文中重新解释；技能通常依附于预先存在的 Agent 结构。本文的持久产物是**共享的 Harness 程序本身**——接受的修复成为普通程序路径，直接编排模型与工具调用，形成不断生长的控制器，而非需在线检索 reinterpret 的经验集合。 ### 3. 语言模型程序的优化（Optimizing language-model programs） 此类研究在不更新模型权重的前提下改进 LLM 系统。 - **提示与指令优化**：APE、OPRO 等优化自然语言指令；DSPy、MIPRO、TextGrad、GEPA 等针对多阶段语言模型程序优化提示与演示示例。 - **工作流与系统设计搜索**：AFlow、ADAS 等利用任务反馈搜索代码表示的工作流或更广泛的 Agent 系统设计。 - **与本文的区别**：上述方法将提示、模块或工作流结构视为可学习对象。本文关注的是**从无策略脚手架（strategy-free scaffold）开始的持续程序增长**：失败执行识别缺失行为，基于追踪的局部编辑将行为加入共享 Harness，更新随任务流累积。 ### 4. Agent Harness 优化（Harness optimization） 近期研究开始直接优化围绕 LLM 的可执行代码与配置。 - **代码与策略合成**：AutoHarness 从环境反馈合成代码约束或完整策略；Meta-Harness 基于源码、候选分数与执行轨迹搜索模型-Harness 代码。 - **基础设施与版本控制**：VeRO 为优化其他 Agent 的 Agent 提供版本控制、结构化观察与评估基础设施。 - **经验驱动的 Harness 调整**：MemoHarness 等从回溯或检索经验中学习，或调整 Harness 以使小模型逼近大模型性能。 - **连续优化中的回归问题**：有证据表明，连续的 Harness 更新若无显式回归控制，可能丢失早期收益。 - **与本文的区别**：本文不仅是代码合成，而是**通过局部的、以失败为条件的优化实现开放式全局 Harness 增长**，训练从仅暴露固定模型与工具接口的无策略脚手架开始。 ### 5. 成本高效的 LLM 与 Agent 执行（Cost-efficient execution） 此类研究关注如何降低推理开销。 - **提示压缩**：LLMLingua 压缩提示长度。 - **模型级联与路由**：FrugalGPT、RouteLLM 通过级联或学习路由选择性调用昂贵模型。 - **高效 Agent 架构**：AgentOccam、WebDreamer 通过更高效的架构减少规划或交互开销。 - **与本文的区别**：这些方法使单次调用更短/更便宜、选择更便宜的调用，或改进固定的推理时策略。本文则从结构上管理上下文——**将重复出现的控制逻辑移入低成本的代码，模型上下文仅保留任务特定证据与语义推理**，在不改变部署模型与工具的前提下降低在线成本。

Q3: 论文如何解决这个问题？

论文提出 **Growing Harness**，一种失败引导的 Agent Harness 训练范式，通过将反复出现的控制逻辑固化为可执行代码来解决上述问题。该方法的核心思想是：从仅暴露固定模型与工具接口、但不编码任何任务求解控制器的**策略无关脚手架（strategy-free scaffold）**出发，利用任务失败反馈逐步生长出可复用的控制程序。具体解决路径包含以下五个相互耦合的机制： --- ### 1. 策略无关脚手架初始化 训练起点为一个极简的可执行程序 $h_0$，其仅包含任务入口和固定的 LLM 后端 $M$ 与工具集 $T$ 的调用接口，**不预设任何 Agent 控制策略**（如 ReAct 式工具调用循环或 Self-Ask 式分解结构）。这使得可执行控制器本身成为可学习的对象，其结构完全由后续的任务反馈塑造。 --- ### 2. 函数级执行追踪与失败定位 针对每个任务 $x_i$，运行时记录完整的执行图 $G_i = (V_i, E_i)$，其中节点涵盖 Harness 函数调用、LLM 调用、工具调用、返回值及运行时错误。任务追踪定义为： $$\tau_i = (x_i, G_i, y_i, o_i, u_i)$$ 其中 $y_i$ 为输出，$o_i \in \{0,1\}$ 为基准评测结果，$u_i$ 包含令牌、成本与运行时开销。 为将失败关联到有限的代码表面，从追踪中提取失败所涉的 Harness 函数集合： $$F(\tau_i) = \{f : f \text{ is a harness function invoked in } G_i\}$$ 这一局部化证据确保优化器无需在每一步处理整个程序，而是聚焦于与失败直接相关的代码切片。 --- ### 3. 失败窗口课程（Failure-Window Curriculum） 训练不针对已解决任务重复优化，而是维护一个容量为 $K$ 的**失败窗口** $W_t$。当前 Harness $h_t$ 在未见任务流上执行，失败实例不断填入窗口直至满额。优化器**联合修复窗口内的所有失败**，以鼓励跨任务共享的控制行为。 窗口的更新遵循： $$W_{t+1} = \{x_i \in U_t : a_i < R_{\max}\} \cup F_t$$ 其中 $U_t$ 为本轮未被修复的任务（保留其更新后的追踪与尝试计数 $a_i$），$F_t$ 为新产生的失败任务，$R_{\max}$ 为单任务最大修复尝试次数。若某任务耗尽预算仍未解决，则从窗口中退役。 --- ### 4. 追踪引导的函数级优化 给定当前 Harness $h_t$ 和失败窗口 $W_t$，离线优化器 $O$（由独立的优化模型 $M_{\text{opt}}$ 驱动）接收： $$Z_t = (h_t, \{\tau_i : x_i \in W_t\}, E)$$ 其中 $E$ 包含离线诊断产物（如评测器反馈、检索文档标识、证据片段等），这些不提供给部署中的 Harness。 为控制搜索空间并关联失败与编辑，优化器被约束为： - **作用域限制**：仅允许修改入口函数 $\text{main}$ 以及窗口内失败追踪所涉及的函数，即 $$A_t = \{\text{main}\} \cup \bigcup_{x_i \in W_t} F(\tau_i)$$ 允许新增可复用的辅助函数，但不得改动未被追踪调用的既有函数； - **编辑预算**：若 $d_{\text{fun}}$ 计数被修改及新增函数数，则要求 $$d_{\text{fun}}(h_t, \tilde{h}_{t+1}) \leq L$$ 优化方向被显式引导：**将确定性的、可跨任务复用的操作（如解析、验证、状态更新、条件查询细化、错误恢复、终止判断）实现为代码**，同时保留 LLM 调用用于任务依赖的语义解释、综合、模糊比较与答案生成。候选必须在语法编译、入口点暴露、接口保留及作用域/预算约束上均有效。 --- ### 5. 保留门验证与事务性回滚 单次修复可能解决当前窗口失败，却损害已习得的早期行为。为此，方法引入**成功优先（success-first）的保留门验证**： 在训练集之外设置独立的门验证集 $G$。每次通过修复累积解决 $Q$ 个任务后，在 $G$ 上评估当前 Harness 的成功率 $\text{SR}_G$。仅当 $$\text{SR}_G(\tilde{h}_{t+1}) \geq \text{SR}_G(h_{\text{gate}})$$ 时，候选 $\tilde{h}_{t+1}$ 才被接受为 $h_{t+1}$，并更新检查点 $h_{\text{gate}}$；否则，**自上一个检查点以来的整个修复序列被回滚**，恢复代码、任务指针、失败窗口、计数器与训练记录至先前状态。 在训练流与窗口耗尽后，还需进行一次最终门评估。若最后阶段的修改未通过门验证，则恢复至上一个被接受的检查点。此机制确保 Harness 的增量增长不会引入脆弱或回归性的补丁，使已验证的能力得以累积。 --- ### 算法流程总结 整体训练循环可概括为（对应 Algorithm 1）： 1. **填充窗口**：运行当前 $h_t$，收集失败至 $W_t$ 达容量 $K$； 2. **局部合成**：优化器基于函数级追踪与诊断产物生成满足作用域和预算约束的候选 $\tilde{h}_t$； 3. **窗口重测**：在 $W_t$ 上重执行候选，得到修复集 $P_t$ 与未解决集 $U_t$； 4. **阈值过滤**：若 $|P_t| < Q$（修复不足），丢弃候选并回退； 5. **门控过滤**：若 $\text{SR}_G(\tilde{h}_t) < \text{SR}_G(h_t)$（保留集回归），丢弃候选并回退； 6. **累积更新**：接受候选成为 $h_{t+1}$，用 $U_t$ 与新的失败 $F_t$ 重构窗口，继续下一轮。 通过上述机制，Growing Harness 将同类型任务中反复出现的控制逻辑逐步移入低成本的持久代码，LLM 仅保留用于语义推理，从而在减少上下文压力与推理调用的同时，实现跨任务的泛化与能力累积。

Q4: 论文做了哪些实验？

论文在**BrowseComp-Plus**与**WebArena-Verified**两个基准上，围绕成功率与推理成本展开了系统评估，并通过收敛分析与消融实验验证了核心机制的有效性。实验内容可归纳为以下五个部分： --- ### 1. 实验设置 - **数据集** - **BrowseComp-Plus**：面向深度检索 Agent 的受控基准，使用固定的人工校验检索语料库。 - **WebArena-Verified**：面向多步骤 Web Agent 的可复现评估基准，包含已修正的任务与确定性评估器。 - 数据划分：每个基准各取 **200 个训练任务**、**50 个门控（gate）任务**、**50 个最终评估任务**。 - **部署模型**（固定权重，不参与训练） - gpt-oss-120b - gpt-oss-20b - Qwen3.5-4B（4B 参数，用于验证小规模模型下的表现） - **基线方法** - **BrowseComp-Plus**：Tool-Calling、Self-Ask、IRCoT。 - **WebArena-Verified**：Tool-Calling、WebDreamer、AgentOccam。 - **评估指标** - **主要指标**：成功率（Success Rate），基于 3 次独立评估运行的平均值。 - **效率指标**：LLM 调用次数、输入/输出 Token 数（千为单位）、执行时间、总在线成本（USD）。 - **统计方法**：任务级聚类自助法（cluster bootstrap），10,000 次重复，固定随机种子 42，报告均值及 95% 置信区间半宽。 --- ### 2. 主实验结果（成功率与成本权衡） - **成功率优势**：在 6 个“基准–模型”组合中的 5 个取得了最高平均成功率，剩余 1 个与最佳结果仅相差 0.7 个百分点（见 Table 1 与 Figure 1）。 - **推理开销大幅降低**：相对于 Tool-Calling 基线： - LLM 调用次数减少 **76.0%–91.8%**； - 在线部署成本降低 **74.4%–98.6%**。 - **跨模型规模稳定性**： - 在 WebArena-Verified 上，Growing Harness 的成功率保持在 **44.7%–45.3%** 的狭窄区间内，几乎不受模型规模影响。 - 相比之下，Tool-Calling 的成功率从 gpt-oss-120b 的 30.0% 骤降至 Qwen3.5-4B 的 **6.7%**，表明 Harness 中固化的代码控制补偿了小模型的推理劣势。 --- ### 3. Harness 生长收敛分析 论文追踪了训练过程中门控集成功率随优化步骤的变化（Figure 3），观察到： - **BrowseComp-Plus**：呈现快速的早期收益。失败引导的修复迅速形成一个**共享的检索与证据验证管道**（query generation → evidence collection → compression → answer checking），该管道被所有任务复用。 - **WebArena-Verified**：训练曲线更为平稳。Harness 围绕一个通用的 LLM 引导浏览器循环，逐步添加针对 Shopping、Reddit、Map 等站点的**专门化处理分支**。由于这些分支以局部方式追加，不会重写其他任务类型依赖的路径，能力得以持续累积，回滚事件较少。 --- ### 4. 消融实验 为验证算法中三个核心机制的必要性，论文在 BrowseComp-Plus（部署模型 gpt-oss-20b，优化器 GPT-5.6-terra）上进行了单因素消融，固定优化 10 步后在 50 个最终评估任务上测试（Table 2 与 Figure 4）： | 变体 | 成功率 | |---|---| | w/o Function-Level Guidance | 18.0% | | w/o Gate Validation | 22.0% | | w/o Failure-Window | 28.0% | | **完整方法** | **36.0%** | - **移除函数级引导**（允许全局任意编辑）：成功率从 36% 降至 18%。全程序编辑导致优化停滞五步后才达到较低平台，验证了**基于失败追踪的局部编辑**对聚焦搜索空间的关键作用。 - **移除门控验证与回滚**：门控成功率一度升至 30%，但随后跌至 16%。这直接展示了回滚机制所要防止的失败模式——修复当前窗口失败的同时破坏早期已习得的行为。 - **移除失败窗口**（$K=1$，逐单失败修复）：成功率降至 28%。说明在**窗口内联合修复多个失败**有助于优化器识别跨任务共享的控制逻辑，而非生成实例特定的补丁。 --- ### 5. 补充分析：任务级效率与可解释结构 - **任务级效率剖面**（Appendix B, Figure 5）：对比了 Growing Harness 与 Tool-Calling 在单次任务层面的 LLM 调用次数、最大输入上下文、单任务成本及总 Token 消耗，直观展示了方法在每次任务执行中的结构性成本优势。 - **习得 Harness 结构的事后抽象**（Appendix B, Figure 6）：将最终程序 $h^\star$ 抽象为可解释的控制流图，显示： - BrowseComp-Plus 习得的结构为**顺序式检索-验证管道**； - WebArena-Verified 习得的结构为**分层控制器**（任务解析器 → 确定性解析器/学习控制例程 → 通用浏览器回退循环 → 完成状态验证器）。 这些实验共同表明：通过失败引导的局部程序增长与门控保护，Harness 能够在显著降低 LLM 调用与成本的同时，将可复用的控制逻辑沉淀为持久代码，并维持跨模型规模的稳定性能。

Q5: 有什么可以进一步探索的点？

基于论文所述范式与实验范围，以下方向具有进一步探索的潜力： ### 1. 跨任务家族的迁移与组合泛化 当前实验分别在单一检索类（BrowseComp-Plus）与单一 Web 交互类（WebArena-Verified）任务家族上训练并评估 Harness。一个尚未回答的问题是：在一个任务家族上生长出的控制结构，能否**零样本或微调后迁移到结构不同但工具重叠的新家族**？更进一步，若部署环境同时面对多个异构任务流（如检索、Web、代码执行交替出现），Harness 是应生长为单一通用控制器，还是自动分化为可组合的模块化专家？这涉及任务家族边界的自动识别与 Harness 结构的组合式增长。 ### 2. 优化器成本与自我优化的闭环 论文中的 Harness 生长依赖一个强大的离线优化模型（如 GPT-5.6-terra）。虽然部署时代理成本大幅降低，但**离线优化阶段的成本与对强大优化器的依赖**未被量化。未来可探索： - 使用较小模型作为优化器，通过迭代自我修正或检索已有修复模式来降低成本； - 让已生长的 Harness 自身承担部分局部修复逻辑，形成“Harness 优化自身”的递归闭环，逐步减少对外部优化器的调用。 ### 3. 细粒度回归控制与选择性累积 当前的门控验证采用**事务性回滚**：一旦保留集成功率下降，即丢弃整个候选序列。这种粗粒度策略可能因一次良好编辑与一次有害编辑的耦合而错失有效更新。更细粒度的机制——例如对单个函数或编辑片段进行孤立评估、或利用版本控制实现分支-合并式的选择性累积——可能进一步提升学习的稳定性与样本效率。 ### 4. 生成代码的安全沙箱与形式化验证 论文在结论中提及实际部署需要沙箱、显式权限边界与代码验证，但未在方法层面解决。由于优化器合成的代码直接参与控制流并调用外部工具，**自动验证 Harness 代码的终止性、工具调用安全性、以及状态空间有界性**至关重要。未来可结合静态分析、符号执行或轻量级形式化方法，为每次候选编辑提供自动化安全证书，而非仅依赖执行层面的基准通过率。 ### 5. 在线持续学习与概念漂移适应 现有范式在离线任务流上批量填充失败窗口。若部署环境面临**非平稳任务分布**（如网站结构更新、工具 API 变更、或用户意图随时间演化），Harness 需要具备在线更新能力而不遗忘先前知识。这要求设计适应概念漂移的动态窗口机制、检测过时控制分支的过时性标准，以及终身学习背景下的门控评估协议。 ### 6. “代码化”与“模型化”决策边界的自适应判定 论文通过启发式引导优化器将确定性操作编码为代码、保留语义推理给 LLM，但这一边界仍依赖人工先验。一个更深层次的问题是：能否**自动学习或理论刻画**给定任务家族下控制决策的最优代码化程度？例如，基于失败模式的可压缩性、跨任务频率或信息论度量，自适应决定某类控制应固化为代码还是保留为模型调用，而非使用固定的优化指令。 ### 7. 多 Agent Harness 的协同生长 当前框架生长的是单一共享 Harness。在复杂环境中，多个专门化 Harness（如一个负责检索、一个负责浏览器控制、一个负责验证）可能通过协同降低单一程序的认知负荷。探索**分布式 Harness 生长协议**——其中每个专家 Harness 独立生长，但共享失败信息与接口契约——可能为多域复杂代理系统提供可扩展路径。 ### 8. 与人类反馈的对齐 当前训练信号完全来自基准评测的二元成功/失败结果。引入**人类对执行轨迹的偏好反馈**（如效率、可解释性、风险规避程度）可让 Harness 生长不仅追求成功率，还符合部署场景的额外约束。如何将人类反馈整合进失败窗口的选择与门控验证标准中，是一个具有实际价值的扩展。

Q6: 总结一下论文的主要内容

该论文围绕**从任务反馈中生长可复用的 Agent 控制程序**这一核心思想展开，提出 **Growing Harness** 范式，旨在将反复出现的推理控制逻辑从 LLM 上下文移入持久化的低成本代码。主要内容可概括如下： --- ### 1. 研究背景与核心问题 标准 LLM Agent 在持续处理同类型任务流时，其 Harness（编排模型与工具调用的可执行代码）往往要求模型在每次任务的上下文中**重新推理并生成相同的控制决策**（如查询细化、观察过滤、错误恢复、终止判断）。这导致： - LLM 推理调用冗余； - 执行历史与上下文不断膨胀； - 部署成本高昂，且小型模型在资源受限场景下难以胜任。 核心问题由此提出：**能否将反复出现的控制逻辑转化为可复用的可执行代码，同时仅保留 LLM 用于任务特定的语义推理？** --- ### 2. 核心方法：Growing Harness 论文提出一种**失败引导（failure-guided）**的训练范式，从一个**策略无关脚手架（strategy-free scaffold）**——即仅暴露固定模型 $M$、工具 $T$ 与任务入口，但不预设任何任务求解控制器（如 ReAct 循环）——出发，让 Harness 程序本身成为学习对象。 关键机制包括： - **函数级执行追踪**：对每次失败执行记录有向无环图 $G_i=(V_i,E_i)$，提取失败所涉的 Harness 函数集合 $F(\tau_i)$，将失败定位到**有限的局部代码表面**。 - **失败窗口课程**：维护容量为 $K$ 的当前失败窗口 $W_t$，优化器**联合修复窗口内全部失败**，鼓励跨任务共享的控制行为： $$W_{t+1}=\{x_i\in U_t: a_i<R_{\max}\}\cup F_t$$ - **追踪引导的函数级优化**：离线优化器仅允许修改失败追踪调用的函数及入口 $\text{main}$，并受编辑预算 $L$ 约束（$d_{\text{fun}}(h_t,\tilde h_{t+1})\leq L$），引导其将确定性控制（解析、验证、循环、恢复）写入代码，保留 LLM 调用用于语义推理。 - **保留门验证与事务性回滚**：设置独立的门控集 $G$，仅当候选 Harness 的门控成功率不低于当前检查点时才接受更新： $$\text{SR}_G(\tilde h_{t+1})\geq \text{SR}_G(h_{\text{gate}})$$ 否则回滚整个修复序列，防止回归与脆弱补丁。 --- ### 3. 实验结果 在 **BrowseComp-Plus**（深度检索）与 **WebArena-Verified**（多步骤 Web 交互）上，使用 4B（Qwen3.5-4B）、20B（gpt-oss-20b）与 120B（gpt-oss-120b）三种部署模型进行评估： - **成功率**：在 6 个基准–模型组合中的 5 个取得最高平均成功率，剩余 1 个仅落后 0.7 个百分点。 - **成本与调用效率**：相对 Tool-Calling 基线，LLM 调用减少 **76.0–91.8%**，在线部署成本降低 **74.4–98.6%**。 - **小模型稳定性**：在 WebArena-Verified 上，Growing Harness 的成功率稳定在 **44.7–45.3%**，几乎不受模型规模影响；而 Tool-Calling 在 4B 模型上骤降至 **6.7%**，表明 Harness 中固化的代码控制显著补偿了小模型的推理劣势。 - **消融验证**：移除函数级引导、门控回滚或失败窗口任一机制，最终成功率均显著下降，验证了三个组件的互补必要性。 --- ### 4. 结论与意义 该研究表明，Agent 无需在每次任务中通过 LLM 推理重建控制逻辑。通过**将可重复的控制结构持久化为代码**，Growing Harness 实现了： - **结构化的上下文管理**：模型上下文仅保留任务特定证据与语义决策，例行控制由低成本代码直接执行； - **跨任务泛化**：习得的行为以可执行程序路径形式累积，而非实例特定的提示补丁； - **资源受限场景的适用性**：为移动设备等环境下的**小型 LLM 部署**提供了保持 Agent 能力的可行路径，即“增长 Harness，而非增长上下文”。
